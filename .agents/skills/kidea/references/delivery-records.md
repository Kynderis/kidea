# Release and operation records through resume

`RECORD_RELEASE`, `START_OPERATION`, `OBSERVE_OPERATION` are operations of the existing public `resume` action. They write evidence records, never run a build, deploy, migration, probe or rollback. Recorded caller readback is not authenticated live health.

First READ the selected project with all required whole-file sources included in `requiredFiles`. Supply the exact returned `expectedBasis`, `expectedProjectId`, current `expectedOwnerId`, and `expectedGit`. The request also contains `proposalRef`, `reviewId` (required for release), `conditionsMet: true`, and a substantive `statement`. The JSON proposal is a selected source outside `.kidea`, read in the basis, not permission.

Permission extends READ with `allowDeliveryRecord: true`, exact `recordPath`, `ownerId`, `statement`, and the confirmed local/no-sync/single-run assumptions. The scope covers updating the current work checkpoint/nextAction, linking the one record in INDEX, the selected record and immutable evidence. Product records live outside `.kidea`, end in `.md`, and their parent directory must already exist. No other source or work progress changes. An existing unindexed file is never overwritten.

All proposals contain `operation`, exact `recordPath`, `nextAction`:

- RECORD_RELEASE: `id, revision, productVersion, components: [{id,version,sourceRefs,artifactRef}], configRefs, schemaRefs, scriptRefs, evidenceRefs, executionPlanRef, recoveryPlanRef`. Refs are whole-file `{path,anchor:null}`. Every component has source and artifact evidence; script and evidence lists are nonempty. The execution-plan JSON contains exactly `stepIds`, a nonempty unique list. Use immutable release-bundle inputs: changing a current release source invalidates it. A current APPROVED review owned by the current item must cover the proposal and every selected source. No caller-supplied approval labels. Revision starts at 1, then increments exactly one for the same release ID; old attempt pins retain old bytes. A round pin to a superseded current release blocks that update; use a separately identified release when retaining that baseline.
- START_OPERATION: `id, releasePath, releaseId, releaseRevision, releaseIntegrity, previousAttemptId, environment, targetId, actor, startedAt`. Integrity is the exact full release-record bytes. Attempt is CREATE-only; a retry uses a new ID/path and links its prior attempt in the same target/environment. No observation is invented at start.
- OBSERVE_OPERATION: `observationId, receiptRef`. Append only to the selected attempt. The receipt JSON contains exactly `operationId, releaseId, releaseRevision, releaseIntegrity, environment, targetId, at, scriptIntegrities, schemaIntegrities, components, steps`. Identity must match the attempt's pinned release, not a newer current release. Components are `{id,result,artifactRef,configRefs,detail}`; steps are `{id,result,evidenceRefs,detail}`. Results are NOT_STARTED/UNKNOWN/FAILED/SUCCEEDED. A successful component requires observed artifact and all config hashes matching the release. Any success also requires observed script/schema identities matching the pinned release. A successful declared execution step requires evidence; arbitrary step IDs are rejected. Partial observations and mixed outcomes stay partial; no aggregate deployment success is inferred.

Capture the receipt through a separately authorized project's real readback method before recording it. An exit code, a desired manifest or a fabricated receipt is not that evidence. Missing response remains UNKNOWN; later append another observation or start a separately authorized retry attempt. Preserve failed/unknown history and all release preimages. Helper tests use explicitly synthetic receipts and certify no service deployment.

The writer rechecks source bytes, tool basis, checkout and projected schema-2 graph. Return `DELIVERY_RECORDED` means metadata bytes verified, not product readiness, review authentication, execution authority or a passed Human gate.

Existing schema-2 attempts may pin their release or its execution plan using fixed local Git versions instead of snapshots. OBSERVE reads the already-bound Git bytes under explicit local Git read permission; it never fetches or substitutes the current release. Unsupported external evidence remains blocked.
